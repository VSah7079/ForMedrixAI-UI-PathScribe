# api/webhooks/engine/

Real, inbound Vercel serverless functions for the Cassette Engine — the four real endpoints an external Engine (or a staging/manual test) POSTs to when it has something to report back to PathScribe. These are the **first real backend serverless functions in this entire project** — confirmed directly (searched the whole repo for any prior `/api` folder, any real Firebase Auth call, any prior Vercel function; found none). `PRODUCTION_MIGRATION.md`'s own reference to an existing function at `api/ai/anthropic/v1/messages.ts` turned out to be aspirational documentation, not something that was ever actually built — confirmed by asking for that file three separate times and getting three different, unrelated files back, then confirming directly with `Test-Path` that no `/api` folder existed in the real repo at all before this work. That means the Web Standard `Request → Response` handler signature every file here uses isn't a deviation from an established convention — there was no prior convention. It's now the de facto one for this project.

**Pattern:** each endpoint follows the same real shape — parse the raw body, verify auth, validate the payload, claim the `messageId` for idempotency, do the real work (a case mutation, a device-status upsert, or a CAPA raise), and return a real, honest status code. Every endpoint logs its own validation failures to a real, structured audit collection rather than silently swallowing them.

## Files

- **`cassette-dispatch-outcome.ts`** — Real endpoint for `CassetteDispatchOutcomeEventPayload` (`src/types/events/`). Persists **every** real outcome — including routine `dispatched` successes, not just problems — as a permanent clinical audit trail (`pending_engine_notifications` collection), per direct guidance's own decision that "cassette A1 dispatched successfully" is a real requirement, not just a notification feed. Never mutates the case itself — same real posture the frontend's own `processCassetteDispatchOutcomeEvent.ts` already established. A real `outcome === 'error'` also raises a real, open CAPA deficiency (`def-cassette-dispatch-failure`) via `raiseSpecimenDeficiency.ts`, per direct guidance's own explicit symmetry decision with block loss/damage — a complete dispatch failure blocks real bench flow the same way a lost block does. `fallback_used`/`prompted` stay history-only, deliberately never CAPA — a color substitution isn't a non-conformity. Real, disclosed gap: this payload carries no `organisationId` field at all (unlike the other three), so the CAPA record's own `organisationId` is simply omitted here, never guessed.

- **`block-exception.ts`** — Real endpoint for `BlockExceptionEventPayload`. Uses the exact same pure mutation rule as the frontend's own `processBlockExceptionEvent.ts` (`src/services/hl7/blockExceptionMutation.ts`) — a real Engine-reported "Lost"/"Damaged" and a Dev Tools simulated one apply the identical business rule, through two different real write paths (this file's own `applyEngineCaseUpdate`, Admin SDK; the frontend's `caseRouter.updateCase()`, client SDK). Writes directly via `applyEngineCaseUpdate` rather than waiting for a browser to be open — a block reported "Lost" is a real, physical fact that needs to land immediately. Also raises a real, open CAPA deficiency (`def-block-lost`/`def-block-damaged`) via `raiseSpecimenDeficiency.ts` — the finding that started this whole piece of work: a real block loss/damage previously only ever touched the block's own status field and a dispatch-history display, never a real, tracked non-conformity, despite being genuinely more clinically significant than a missing timestamp (potentially unrecoverable diagnostic material). Also writes a `pending_engine_notifications` entry so a tech's already-open case view gets a real-time toast without a manual refresh — that write is deliberately separate from the CAPA raise, since they serve genuinely different audiences (a bench tech needs to know now; a QA reviewer needs a tracked record).

- **`material-location.ts`** — Real endpoint for `MaterialLocationEventPayload`. Same real pattern as `block-exception.ts` — shares its own pure mutation rule (`src/services/hl7/materialLocationMutation.ts`) with the frontend's `processMaterialLocationEvent.ts`, writes via `applyEngineCaseUpdate`. Covers all 8 real target levels (specimen/block/slide/aliquot/decant/decant_slide/decant_aliquot, plus the two case-level matrix_block/matrix_slide levels that need no `specimenLetter` at all). Does **not** raise a CAPA record — a location update is real, useful history, not itself a non-conformity the way a loss/damage/dispatch-failure is.

- **`engraver-status.ts`** — Real endpoint for `EngraverStatusEventPayload` — the fourth real inbound event, and the only one that's genuinely *current state* rather than an append-only event log. Writes via `upsertEngraverStatus.ts` (below), never `pending_engine_notifications` — a device's own coarse status lives in its own `engraver_devices` document, one per device, upserted in place. Deliberately coarse by design, per direct guidance's own explicit correction: no per-hopper fill percentages, no hardware telemetry — `status` (online/engraving/warning/fault/offline) plus structured `supplyWarnings` (a closed set of real functional states — `CASSETTE_SUPPLY_LOW`/`CASSETTE_SUPPLY_DEPLETED`/`COLOR_UNAVAILABLE` — each optionally tied to a real `CassetteColorDefinition.key`) and free-text `warnings` for non-supply issues. PathScribe never models which physical hopper feeds a color — that's the Engine's own, permanently separate concern (`evaluateCassetteRouting.ts`'s own header already established this same boundary for cassette routing itself).

## `_lib/` — shared backend-only helpers

- **`firebaseAdmin.ts`** — Shared Admin SDK init, one singleton per cold start. Real, deliberate dual mode: when `FIRESTORE_EMULATOR_HOST` is set, connects to a real local emulator with no credential at all (a real production credential should never load into a process about to point at a local emulator); otherwise requires `FIREBASE_SERVICE_ACCOUNT_KEY` (the full service-account JSON, as an env var string — serverless functions have no persistent filesystem to read a real key file from). **Real, disclosed, unresolved gap**: the actual client-side Firebase config (`src/firebase/config.ts`) is still placeholder (`apiKey: "YOUR_API_KEY"`, `projectId: "your-app-id"`) — confirmed directly. That means every client-side Firestore read this session built (`fetchEngraverDevices.ts`, `fetchGlobalDeficiencies.ts`, `usePendingEngineNotifications.ts`, etc.) has never actually reached real data in a real browser, independent of anything about this folder. Whether a real Firebase project even exists yet for this backend side either is *also* unconfirmed — last known status: the team was being asked to check.

- **`verifyEngineAuth.ts`** — Shared-secret (`ENGINE_WEBHOOK_SECRET`, header `X-API-Key`/`X-Engine-Signature`) plus optional HMAC signature verification (`ENGINE_WEBHOOK_HMAC_SECRET`, header `X-Engine-Hmac-Signature`) — independently toggleable, since a real deployment might only support one depending on what the actual vendor Engine can do. Fails closed: if neither secret is configured, every request is refused, on the theory that an operator who hasn't finished setup shouldn't accidentally accept unauthenticated traffic. Constant-time comparison throughout (`timingSafeEqual`) — a plain `===` on a secret leaks timing information about how many leading bytes matched.

- **`idempotency.ts`** — `claimMessageId()`: real, Firestore-native idempotency via `create()` (fails atomically on conflict) against a `processed_messages/{messageId}` document — the fix for the three original `process*Event` functions' own in-memory `Set`, which only ever worked within one long-lived browser tab and gives no real guarantee across separate, memoryless serverless invocations.

- **`applyEngineCaseUpdate.ts`** — The real, backend-only, Admin-SDK equivalent of `caseRouter.updateCase()` — deliberately **not** a method on `FirestoreCaseService.ts`, since that file is client-bundled and `firebase-admin` cannot run in a browser at all (a real, serious correction made mid-session after the original proposal put it there). Real transaction: reads the case's current `specimens`/`matrixBlocks`/`version`, hands them to the caller's own `mutate` callback, writes the result back with a real `version + 1` increment — the same real optimistic-concurrency contract `FirestoreCaseService.updateCase()` already uses, so a concurrent client edit can't silently overwrite what the Engine just applied.

- **`upsertEngraverStatus.ts`** — Real, transactional upsert with a staleness guard: an event's own `timestamp` is compared against the currently-stored `lastReportedAt`; an older or exactly-equal timestamp is rejected (`stale-ignored`), never allowed to overwrite genuinely newer state — a real, out-of-order redelivery (a delayed retry arriving after a newer status already landed) can't corrupt current state.

- **`raiseSpecimenDeficiency.ts`** — The real, backend-only equivalent of `ISpecimenDeficiencyService.raise()` — reachable from a webhook the way the client-only `mockSpecimenDeficiencyService.ts` (localStorage-backed) never can be. Deliberately scoped to `raise()` alone — no `resolve`/`containImmediately`/`verifyEffectiveness`/`raiseAndResolve` here; those are real, legitimate CLIENT actions (a QA reviewer working through the UI), now built separately under `api/qa/deficiencies/` (see that folder's own README).

- **`logIntegrationError.ts`** — Real, structured audit logging for every `400` a webhook rejects — a schema mismatch, a missing field, an unsupported enum value some vendor Engine build sent. Writes to a new `integration_errors` Firestore collection (chosen after confirming `AuditLogger.ts` only writes to `console.debug` today — no real Firestore audit store existed to extend). Deliberately Vercel-native and vendor-neutral: considered and explicitly declined real AWS CloudWatch/Azure Application Insights integration, since this project's actual, confirmed hosting platform is Vercel, and a shared-secret embedded in a browser bundle can't provide real security the way a server-side-only secret can. A failure to write this log entry is always caught and console-logged, never allowed to turn an otherwise-correct response into a `500`.

## Auth posture across this whole folder

None of the four endpoints authenticate a caller the way a typical app authenticates a human user — `verifyEngineAuth.ts`'s shared secret is the only real gate, and it's specifically designed for a **server-to-server** caller (the Engine) that can keep a secret server-side. This is a deliberately different, and currently unresolved, question from the sibling `api/qa/deficiencies/` folder, whose real callers are this app's own frontend — see that folder's own README for why a shared secret doesn't help there, and what's still open.

## Testing

- **Unit tests** (`*.test.ts` alongside each endpoint and each `_lib` file) — mock every dependency, run in the normal `npm test` suite, verify each handler's own logic (auth rejection, payload validation, idempotency branching, status-code mapping) without touching real Firestore.
- **Integration tests** (`_lib/*.integration.test.ts`) — real Firestore Emulator tests for `applyEngineCaseUpdate` (concurrent-mutation transaction retry, deterministic version increments), `upsertEngraverStatus` (the real staleness guard against real Firestore read-then-compare-then-write semantics), and `idempotency` (a real duplicate `create()` genuinely failing). Skip cleanly (never fail) when `FIRESTORE_EMULATOR_HOST` isn't set — confirmed directly by running them with no emulator configured and fixing a real bug where the original version threw instead of skipping (a `describe.skipIf` body still executes eagerly to register child tests; only hook/`it` bodies actually respect the skip — Firestore init had to move into a `beforeAll`). **Never actually run** — this sandbox has no network access to `storage.googleapis.com`, where the real emulator binary downloads from, confirmed by trying and getting a real `403`.
- **Manual verification** — `PathScribe-Engine-Webhooks.postman_collection.json` and `verify-webhooks.ps1` cover all four endpoints against `vercel dev` or a real staging URL: auth failures, malformed payloads, happy paths, redelivery, stale telemetry, case-not-found. Neither has ever actually been run against a real deployment.

## Security rules

`firestore.rules.engine-webhooks.txt` — a fragment, not a full file. **Correction (Batch 324):** the repo-root `firestore.rules` does exist. It covers cases, ancillary staging, the audit log, platform config and (since Batch 320) AI models, but not yet the collections below, so this fragment still needs merging into it. Every collection this folder writes to (`processed_messages`, `integration_errors`) is locked to Admin-SDK-only access; `engraver_devices`/`pending_engine_notifications`/`specimen_deficiencies` (client-read collections owned by sibling folders) are open-read/no-client-write. That open-read posture is a real, disclosed, temporary compromise: this app has **no real Firebase Authentication anywhere** — confirmed directly (`src/contexts/AuthContext.tsx` is a custom, `localStorage`-backed mock with a literal hardcoded array of real people's plaintext email/password credentials; zero calls to `signInWithEmailAndPassword`/`getAuth()` exist anywhere in the codebase). Until real auth exists, `request.auth` is always `null`, so no rule can genuinely distinguish a legitimate reader from anyone else — open-read was the least-bad option, not a real access-control decision.
