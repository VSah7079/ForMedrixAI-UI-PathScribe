## A real mistake made and caught mid-build, worth restating in full
While fixing `computePendingBatchQueue.ts`'s own long-documented facility-scoping gap, the first attempt used `Case.facilityId` — which turned out to be wrong. Its own doc comment says it's "the institution that **sent** the specimen" — the referring facility, not the performing lab. Using it would have scoped the queue by who sent the specimen in, not which bench is actually processing it — backwards for the real question this queue answers. Caught by re-reading the field's own comment rather than trusting the name. The correct field, confirmed directly against `resolveCaseAccess()`'s own real tenant-scoping logic and real seed data (`originHospitalId: 'c-fenwick-general'` — the same real id space `ScanStation.facilityId` already uses), is `Case.originHospitalId`.

A second real correction, also worth naming: `computeDisposalQueue.ts` was assumed to be the template to copy for the facility filter (the file's own old header pointed at it). It isn't — that queue resolves facility from an item's own scan-derived `locationHistory`, but the pending-batch queue's entire premise is items that have never been scanned. Copying that pattern verbatim would have left every scoped query empty. The correct fix is simpler: filter directly on the case's own known facility, since a never-scanned item hasn't moved anywhere since accessioning.

## What's real and working end-to-end

- **`WorkstationGroup`** (`services/workstationGroups/`) — the first-class entity from PS-289: `discipline` (Histology/Cytology/Molecular ship with real, populated `functionalArea` sets — Histology's reuses the exact, already-established `SCAN_STATION_WORKFLOW_STAGES` vocabulary rather than inventing a parallel one; Autopsy is a valid, reserved discipline value with a deliberately **empty** functional-area set, per PS-261's own explicit deferral — creating an Autopsy group is honestly rejected until that ticket gives the discipline a real, populated list of its own). `performingLabFacilityId` is required (unlike the optional facility scoping on the Fixative/ContainerType/DeficiencyType catalogs) — this entity exists specifically to close a real scoping gap, not to inherit a "global by default" convention built for a different reason. `qcEnforcementMode`/`defaultActionGroupId`/`allowedActionGroupIds`/`defaultActionId`/`dedicatedPageRoute` are defined for later phases — see "not built yet" below.
- **A real correction to my own earlier PS-289 proposal**: that proposal put `memberStationIds` as an array on the group. Building it, the standard, safer pattern for "one group has many stations" is the FK on the station side instead — `ScanStation.workstationGroupId?` — avoiding two sources of truth that could drift apart.
- **Facility-match enforcement**: `mockScanStationService.update()` now rejects assigning a station to a group scoped to a different real facility — checked at the actual assignment point, not just documented on the field.
- **`ActionGroup`** (`services/actionGroups/`) — genuinely new entity, `{ id, name, actionIds, status }`, a real many-to-many bundle. Nothing like this existed before.
- **`SystemAction.stationProfiles?: string[]`** — reuses the same `functionalArea` values, not a separate tag vocabulary. `getEligibleActions()` extended with a third, independent "OR" branch (station profile match), additive alongside the existing `GLOBAL_CATEGORIES`-or-context rule — never replacing it. Both voice and keyboard matching share this one function, so they can't silently drift apart.
- **`NavBarScanStation.tsx`** — the real, live wiring: selecting a station resolves its `WorkstationGroup`, and pushes that group's `functionalArea` into the Action Registry via a new `setCurrentStationProfile()`, automatically — no separate step for the technician. Clears correctly when no station is selected, or when a selected station has no group.
- **`ActionsTab.tsx`** — the admin "Station Profiles" multi-select on the Edit Action modal, pulling its options from the same real, shared `FUNCTIONAL_AREAS_BY_DISCIPLINE` constants — not a second, hardcoded list.
- **`computePendingBatchQueue.ts`** now takes a real `facilityId: string | undefined` parameter, scoping via `Case.originHospitalId` (see the correction above). **`PendingBatchQueuePage.tsx`** resolves station → facility the same real way `DisposalQueuePage.tsx` already does, and shows which facility the queue is scoped to (or an honest "no station set" notice).
- No migration was attempted from `ScanStation.workflowStage`'s own free text — existing stations start genuinely unassigned; an admin assigns membership deliberately going forward.

## What's genuinely not built yet — flagged plainly
- No admin UI exists for creating a `WorkstationGroup` or `ActionGroup` through the app itself — both have full, tested CRUD services, but only reachable via code/tests today, not through any screen.
- `defaultActionGroupId`, `allowedActionGroupIds`, and `defaultActionId` are defined on the type but not yet consumed anywhere — only the broader `functionalArea`-tagged eligibility is live end-to-end. The more specific "load this exact action group" and "fire this exact default action on the next scan" mechanisms are real, separate, unbuilt follow-up work.
- `qcEnforcementMode` and `dedicatedPageRoute` are unused placeholders, as expected — the Gating Strategy logic and PS-284/285/286's own bench pages don't exist yet either.
