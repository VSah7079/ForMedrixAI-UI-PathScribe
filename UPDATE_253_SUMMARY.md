# PathScribe Update 253 — Summary

The final piece of the Stain QC Module's Gating Strategy (PS-289/PS-292): actually wiring the decision logic from update-252 into the real sign-out flow. Before this update, resolveStainQcGate() was real and tested but connected to nothing — a case could sign out regardless of what it would say. That's no longer true.

## A real, honest limitation found and worked around, not papered over
Before writing the "gather" function, I checked whether a stain order can be reliably matched back to its own StainType record — this is essential for the per-stain override half of "instrument-level default, per-stain override." It can't, not safely: StainOrder.stainName is explicitly documented in this codebase as "display name only for this pass — not yet a real foreign key into the Stain Dictionary." A name-based fuzzy match would risk silently misapplying a compliance-critical enforcement mode, so I didn't build one. checkStainQcGate() resolves the effective mode from the batch's own WorkstationGroup default only. The per-stain path is not removed — resolveEffectiveQcEnforcementMode() (built in update-252) already accepts it — it's just genuinely unreachable until StainOrder gets a real stainTypeId, which is separate, pre-existing follow-up work, not something this update should paper over with a fragile guess.

## What changed

- checkStainQcGate.ts — the async "gather" half, mirroring checkPreAnalyticAndFixativeGates()'s exact shape (a case in, an array of blocking items out). Resolves the real chain Batch.stationId -> ScanStation.workstationGroupId -> WorkstationGroup.qcEnforcementMode, matches each stain to its real batch via the same slideIdentifier() convention processMicrotomyScan already uses, then calls the already-tested pure resolver per stain.
- StainQcGateModal.tsx — mirrors FixativeTimeGateModal.tsx's real, established shape (a hard block, not a dismissible warning). Grouped by real batch, not by individual stain, since the confirmation itself is a batch-level action. A real, deliberate design choice: a confirmed instrument failure (blocked-failed) has no self-service resolution here at all — it points to the QA Deficiencies tab instead. Overriding a known failure from this modal directly would be a real, dangerous shortcut around the Contain/Escalate-to-CAPA workflow this session already built for exactly this deficiency type.
- useSignOutWorkflow.ts — the gate is now checked at both real sign-out entry points (handleSignOutConfirm for Orchestration Mode, finalizeCase for Assist Mode), in the same position the fixative gate already occupies: after the more foundational pre-analytic/fixation gates, before either path proceeds.
- SynopticReportPage.tsx — new state, the modal's own rendering, and a handleStainQcGateContinue handler — simpler than its fixative-gate counterpart, since the real confirmation itself already persists inside the modal directly (via confirmQcVisualRead()) rather than being handed back up as data still needing to be saved.

## Two real bugs caught and fixed while building this
1. checkStainQcGate.ts initially referenced batch.workstationGroupId — that field lives on ScanStation, not Batch. Also referenced caseData.accessionNumber, which doesn't exist on Case at all; the real, working field, confirmed against actual existing code, is caseData.accession.fullAccession.
2. The first version of checkStainQcGate.test.ts never actually created its test case via caseRouter.createCase() — it only built a plain object and called the checker directly. This meant addItemByScan() was silently failing to resolve the slide against a real case, so no batch item was ever added. One test (Enforced mode, expecting a real block) caught this directly; another (Auto-Resolve, expecting no block) had been passing for the wrong reason — it would have passed either way. Fixed by seeding a real case via caseRouter.createCase(), matching the exact working pattern already established in computePendingBatchQueue.test.ts.
