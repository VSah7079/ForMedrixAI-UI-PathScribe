# PathScribe Update 254 — Summary

Section 2.2/2.3 of the original Stain QC Module spec: batch-manifest scanning with automatic control-slide appending. When a reagent lot requiring a target control is added to a new Staining batch, a real control slide (a synthetic case, accessioned exactly the way a real patient case would be) gets automatically created and appended to that same batch's manifest, if one isn't already there.

## Design questions resolved before building, per direct guidance
- Unit of coverage: the real analytical run - i.e. the batch itself, not a calendar day, reagent lot, or bench. Each new Staining batch needs its own fresh control; nothing is reused across batches.
- Pass/fail determination: the same StainQcGate mechanism already built (update-253) - batch-level stainingInstrumentStatus/qcVisualReadConfirmation. This update's own job stops at the earlier, setup-time question (is a control present at all); it does not duplicate or reinvent pass/fail tracking.
- Which stains need this: refined mid-build, per direct follow-up, into two real, independent toggles rather than one - requiresTargetControl (does this stain need a target control at all - IHC, target-specific special stains, ISH) and allowControlAutoAppend (should the system generate the slide automatically, or does the lab handle it via an internal tissue control or manual SOP). Both are real, per-stain fields on StainType - never a computed category default, since real exceptions exist within "Special Stain" itself.

## A real, important design correction made mid-build, worth restating
The very first design (before this update's own final shape) risked running into the same StainOrder.stainName FK gap flagged in update-253 - inferring "does this scanned slide need a control" from a patient specimen's own stain order name. Checked directly before building: ReagentLot.stainTypeId (built in update-246) is already a real, complete FK. So the real trigger for this feature is reagent-lot selection at batch creation - the same real workflow the original spec's own section 2.2 describes ("scanning reagent or kit barcodes at the bench prior to a run") - not an inference from the patient side at all. This sidesteps the FK gap entirely rather than working around it.

## What changed
- StainType.requiresTargetControl / allowControlAutoAppend / defaultControlTissueType - seeded with real values on the stains the guidance explicitly named: all real IHC entries (Ki-67, ER, PR, HER2, p63/CK5/6, PD-L1 both clones, MLH1/MSH2/MSH6/PMS2) and PAS/GMS/Trichrome get both toggles set true, with a real default control tissue per stain. H&E gets neither, per direct confirmation. Deliberately left unset on Immunofluorescence, Molecular, and Cytology entries - the guidance didn't explicitly address them, and silently inferring by analogy on a compliance-relevant field isn't the right call. Molecular-category stains (including the real, seeded FISH entries) already run through a separate batch system with their own control mechanism and were never in scope here regardless.
- Case.controlSlideContext - mirrors proficiencyTestContext's own, already-established real pattern exactly: a synthetic case, accessioned the same real way as any patient case, with one real, structural marker field. A normal-shaped accession (S26-CTRL0001-CTL-001) with unmistakably synthetic patient content, matching the existing convention rather than inventing a new format.
- shouldAutoAppendControl.ts - the pure decision function, checking both toggles together.
- ensureControlSlideAppended.ts - createControlSlideCase() builds the real, synthetic case and returns its real slide id; batchHasControlForLot() checks a batch's own real items against their own case data directly, not a separately-maintained index that could drift.
- mockBatchService.create() - wired in: for every real reagent lot selected on a new Staining batch whose stain requires an auto-appended control, and isn't already represented in this same batch, one real control item is created and appended before the batch is even persisted. Never blocks batch creation on a failure here - a bad reagent lot id or a resolution failure is a real, separate problem the tech's own physical batch creation shouldn't be held hostage to.
