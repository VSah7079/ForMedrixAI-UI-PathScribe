# PathScribe Update 240 — Summary

Cytology now has a real amendment/correction mechanism — the largest, most-flagged gap named in this session's own gap review. Confirmed at the start of this work: nothing existed before this — no dedicated service, no UI, nothing. Once a Cytology case was signed out, there was no way to correct it in this app.

## The architecture question investigated before designing anything

`CytologySignOutRecord`'s own header comment states a real, deliberate posture: "always written, never edited." That single line ruled out mirroring Surg Path's own amendment mechanism directly — Surg Path unlocks and re-edits an existing `SynopticReportInstance` in place; doing the same to a `CytologySignOutRecord` would violate this module's own established audit architecture. The correct design instead follows the same pattern this module already uses everywhere else for a genuine, distinct review event: a correction creates a **new**, separate `CytologyReviewRecord` (the corrected findings) and a **new**, separate `CytologySignOutRecord`, linked back to the one it corrects — never a mutation of history. The specimen's own real, current result is always the most recently signed record for it; the full, real chain of every prior sign-out stays queryable forever via `getBySpecimenId()`.

## What changed

- **`CytologySignOutRecord`** gained `amendsRecordId?: string` — undefined on every original sign-out, set only on a record created by the new correction function below.
- **`buildCytologyOruR01Payload.ts`** generalized from a hardcoded `resultState: 'FINAL'` to `'FINAL' | 'CORRECTED'`, with a new `narrative.previouslyReportedAs` field mirroring `buildOruR01Payload.ts`'s own identical field. Deliberately no `'ADDENDUM'` value at all — Cytology genuinely has no addendum concept of its own; a correction always replaces the specimen's single Final Diagnosis, there's no separate, supplemental result to append the way Surg Path's multi-instance model allows.
- **`CytologyOutboundResultQueueEntry`**'s own `resultState` had the identical `'FINAL'`-only problem — caught directly by `tsc` when generalizing the payload builder, fixed the same way.
- **New: `dispatchCytologyAmendedCaseInstance.ts`** — the real, dedicated electronic dispatch for a genuine Cytology correction, mirroring `services/reports/dispatchAmendedCaseInstance.ts`'s own shape (scoped to one specific record, no dedup — each real correction is its own, distinct, legitimate event that should always genuinely dispatch) but built against Cytology's own real data model and outbound queue. 7 tests.
- **New: `releaseCytologyCorrection.ts`** — the real orchestration. Finds the specimen's own most recently signed prior record (the real "before" state — its `reportContent.primaryInterpretation`, taken verbatim, is the real "previously reported as" text, no diffing or reconstruction), creates the new review and new, linked sign-out record, then calls `publishReportReleasedEvent` with `source: 'CYTOLOGY'`, `reportType: 'CORRECTED'`. Deliberately accepts the same real patient/order/specimen parameter shape `resolveCytologyReportContent.ts`'s own established signature already takes, so a future UI caller can reuse the exact context-gathering code the initial sign-out handler already has, rather than this function re-deriving it and risking drift. 6 tests.
- **`publishReportReleasedEvent.ts`**: the `CORRECTED` case now branches on `source` — Cytology routes to the new dispatcher; an omitted or `SURGPATH` source falls through unchanged to the existing, already-working Surg Path path (directly, separately tested to confirm the fallthrough introduces no regression there). Cytology's own `ADDENDUM` events are never routed to its dispatcher, even if one were ever published — confirmed with a dedicated test.

## Verification
`tsc` clean throughout. Full suite: 445 files, 3888 tests, all passing (up from 443/3866 — 22 new tests across 4 files, including 5 new routing tests in `publishReportReleasedEvent.test.ts`).

## Honest scope — deliberately not built in this pass
- **No UI trigger exists yet.** `releaseCytologyCorrection.ts` is real, tested, and ready to be called, but there's no "Correct Diagnosis" action in `CytologyScreeningPage.tsx` to call it. Given that page's own size and the risk of adding a new correction-mode UI state to it, this was scoped as its own, separate follow-up rather than attempted in the same pass as the underlying mechanism.
- Not verified live in a browser, for the same reason — no UI exists yet to click through. Relying on the layered, direct unit coverage across all four new/changed files instead.
