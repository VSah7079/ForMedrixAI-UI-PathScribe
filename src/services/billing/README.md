# services/billing/

The real, minimal RVU (Relative Value Unit) infrastructure this app never had — built specifically because `ProductivityTab.tsx`'s and `ContributionDashboardPage.tsx`'s RVU tiles were both hardcoded, with no real CPT-to-RVU mapping or per-case RVU field anywhere in this codebase to compute from.

**Real, versioned as of a direct follow-up question ("is there a UI to update the table?" / "these need to be versioned, correct?").** The original version of this folder was a single, static, unversioned constant — real, verified CMS data, but with no way to update it without a code change, and no way to protect historical case RVU totals from silently changing if it ever was updated. Both gaps are now closed.

**Pattern:** `codeMapTable.ts` is a pure, static reference table plus pure calculation functions (no service, nothing to mock). `RvuTableVersion.ts` / `IRvuCodeMapService.ts` / `mockRvuCodeMapService.ts` follow the standard interface/mock pattern used everywhere else in this app.

## Files

- **`codeMapTable.ts`** — `CODE_MAP_TABLE`: the original, real, curated CPT → work RVU mapping (five common anatomic pathology codes: 88302, 88304, 88305, 88307, 88342), values verified via direct search against the current CMS 2026 Medicare Physician Fee Schedule (PPRRVU2026_Apr_nonQPP). `computeWorkRvuForCodes()` sums real work RVU for a case's assigned codes against a given set of entries — generalized to accept any real entry set (e.g. a specific historical version's entries), defaulting to `CODE_MAP_TABLE` so existing callers are unaffected. `ruleBasedDefaultCptCodes()` is the honest, rule-based fallback for the fact that `Case.coding.cpt` is genuinely never populated anywhere today (no manual-entry UI exists) — one 88305 per real specimen, matching CMS's own per-specimen billing rule. **`parseRvuUploadRows()`** — real fix, from a direct follow-up question about whether the real, actual CMS PPRRVU file shape could be anticipated in advance rather than guessed at later: verified via direct search (not assumed) that the PPRRVU file is itself genuinely public, CMS-derived data — not AMA-licensed — and recognizes its real column names (`HCPCS` for the code, `Status Code`, `MOD`) alongside this app's own simple template. Applies CMS's own documented rule that only status `A`/`R`/`T` carry a usable RVU value (a real file lists thousands of bundled/invalid codes too) and skips modifier-specific rows, since this app's code map doesn't model modifiers. A real, unmodified CMS PPRRVU download can be uploaded through the admin UI today, right now, no AMA license needed for this part — the license gap that remains is specifically the official, full-text AMA code *descriptions*, not the work RVU values themselves.
- **`RvuTableVersion.ts`** — **New.** The real versioning model: `RvuTableVersion` is an immutable, effective-dated snapshot of the whole code map at a point in time — same "never edit history, only add a new record" principle this app already uses for `ReportVersionRecord`/`DelegationRecord`/`ReconciliationRecord`. `resolveVersionEffectiveAt()` is the pure, synchronous resolver that's the actual point of all this: given a real date (e.g. when a case was genuinely finalized), returns the real version that was in effect then — not whatever's marked active today.
- **`IRvuCodeMapService.ts`** / **`mockRvuCodeMapService.ts`** — **New.** Real CRUD for versions: `getAllVersions`, `getActiveVersion`, `getVersionEffectiveAt` (the async, storage-backed twin of `resolveVersionEffectiveAt`), `createVersion` (the only way to change the code map — never edits an existing version in place), `activateVersion` (exactly one version active at a time; does not affect historical resolution, which is date-based, not active-flag-based). Seeded with the original five-code table as the first real version.
- **`RvuCodeMapSection.tsx`** (`components/Config/System/`) — **New.** The real admin UI, wired into Config → System → "RVU Code Map". Built to be genuinely easy to use, per direct request: active version front and center, older versions collapsed behind a single toggle by default (never deleted, but shouldn't clutter the common case), real spreadsheet upload (matching this app's own established `SpecimenDictionarySection.tsx` pattern — download a real template, upload a real `.xlsx`/`.csv`, preview before anything is committed), "activate immediately" checked by default. Real bugs caught and fixed while building it: an early version invented CSS classes (`ps-banner`, `ps-btn--secondary`) that don't exist anywhere in `pathscribe.css` — checked directly and fixed to the real, verified `ps-btn-secondary`; and it would have shown a raw user ID instead of a resolved name.

## Charge Capture work — CptWorkRvuEntry → BillingDictionaryEntry, real Billing Dictionary rows

Real, direct guidance, cross-checked against an external "Order Type Mapping" spec before building: `CptWorkRvuEntry` renamed to `BillingDictionaryEntry` (type-only — `code`/`workRvu`/`description` property names deliberately kept as-is, since a live CMS-PPRRVU-file upload parser and this folder's own admin UI both already construct/render those exact names; renaming them would touch working code for zero functional gain). **Still open, genuinely unbuilt**: the "Service Charge Object" — a real, persisted, per-case structure that `billingCode` suggestions ultimately resolve into (richer than today's flat `Case.coding.cpt: string[]`/`Specimen.coding.cpt`/`Block.coding.cpt`), feeding `services/hl7/dftBuilder.ts`'s Category C `ChargeCaptureEventPayload` at finalization. ## `ServiceChargeRecord` — real, permanent, resolved snapshot (Charge Capture, closed)

Per direct, explicit guidance (immutability/auditability/regulatory-safety reasoning, matching how Epic Resolute/Cerner ProFit/Xifin/Telcor/Waystar/Change Healthcare all expect stable historical CPT lines): resolution happens exactly ONCE, at finalization, and the resolved CPT/HCPCS/RVU/modifier values are persisted permanently — never re-resolved against the Billing Dictionary again after creation, even if CMS/AMA/the enterprise's own billingCode→CPT mappings change later.

- **`types/billing/ServiceChargeRecord.ts`** — the real, immutable record type, same "never edit history, only add a new record" convention as `ReportVersionRecord`/`AmendmentRecord`/`ReconciliationRecord`. Keeps `billingCode` alongside the resolved values (deliberate redundancy — the permanent audit trail for "what internal rule produced this charge," independent of the resolved CPT), `billingDictionaryVersionId` ("what ruleSetId produced the charge," a real `RvuTableVersion.id`), and `reportVersionRecordId` ("what documentation existed" — a real, working link to the signed report version, deliberately NOT tied to the synoptic `requiredFields` completeness counter, which has its own real, already-disclosed gap — see `pages/SynopticReportPage/hooks/useSignOutWorkflow.ts`'s own comment).
- **`resolveServiceCharge.ts`** — **New.** `resolveServiceCharge()` is the one real place a `billingCode` ever gets resolved into a full `ServiceChargeRecord`, given a specific set of `BillingDictionaryEntry[]` (a specific historical version's entries, resolved for the case's real finalization date via `getVersionEffectiveAt`, not whatever's active today). Returns `null`, never a fabricated record, for an unrecognized `billingCode` — same honest-gap posture as `computeWorkRvuForCodes`'s own `unrecognizedCodes`. `resolveServiceCharges()` is the real batch entry point for a whole case's worth of applied `billingCode` suggestions at once, assigning real, distinct `sequencePosition` values only when a `billingCode` genuinely repeats within the batch (e.g. two real `IHC-ADDL` stains). Ids are deterministic (`caseId`/`sourceLabel`/`billingCode`/`sequencePosition`), not random — reprocessing the same real event reliably produces the same id rather than a duplicate, matching this app's own idempotency expectations elsewhere.
- **Known, disclosed staleness flagged, not yet reconciled**: `services/hl7/dftBuilder.ts` still reads `specimen.coding.cpt`/`block.coding.cpt` directly as if those hold final CPT strings — as of this work, they hold `billingCode` labels instead, and the real CPT/RVU/modifier now lives on `ServiceChargeRecord[]`. That file has zero real callers today (documented pre-integration scaffolding — no transport exists yet), so the rewire is deliberately left as real, separate, sequenced future work rather than bundled in here — flagged directly in that file's own header so whoever wires up real transport later finds the note first.

## `BillingRuleVersion` — real, per-billingCode append-only versioning (supersedes the whole-table model above for Charge Capture)

Per direct, explicit, fully-specified guidance: `RvuTableVersion`'s whole-table snapshot model (above) was the wrong grain for Charge Capture — correcting one code's RVU shouldn't require re-snapshotting every other code. `types/billing/BillingRuleVersion.ts` versions each `billingCode` independently: `(billingCode, version)` is the real unique key, never edited in place, only ever appended to with `status: 'RETIRED'`/a real `effectiveTo` set on the row it supersedes.

- **`resolveBillingRuleAt.ts`** — pure resolver, exact algorithm per direct guidance: `billingCode` matches, `effectiveFrom <= dateOfService`, `effectiveTo` is null or `>= dateOfService`, `status == 'ACTIVE'`. Status is checked independently of the date window — a RETIRED row is never selected even inside its own historical window, which is fine specifically because `ServiceChargeRecord` already permanently snapshotted its resolution back when that version was still ACTIVE.
- **`IBillingRuleService.ts` / `mockBillingRuleService.ts`** — real CRUD; `version` is always server-computed (never caller-supplied) so `(billingCode, version)` uniqueness can't be violated; `changeReason` required for any version past the first; real CPT required on every version — "customers may create custom billingCodes, but they must map to real CPT/HCPCS/RVU values... never invent their own," per direct guidance. Seeded with version 1 for all 10 existing billingCodes, migrating the honest, disclosed RVU gaps forward unchanged.
- **`modifiersAllowed`/`quantityRules`/`bundlingRules`/`documentationRequirements`** — real, stored fields, confirmed directly (grepped across the whole codebase) to be informational/reference only. Nothing reads them for validation or enforcement anywhere — matches the Thread 1/Thread 2 split exactly.
- **`resolveServiceCharge.ts`/`ServiceChargeRecord.ts` rewired** onto this model — `billingDictionaryVersionId` (whole-table) replaced by `ruleVersion`/`ruleSetId` (the exact per-billingCode version).
- **`services/hl7/dftBuilder.ts` rewired** — the previously-disclosed staleness above is now resolved. `buildDftP03ForCase` takes a case's real `ServiceChargeRecord[]` directly and builds one FT1 per real charge, sourcing `cptCode`/`cptDescription`/`modifier`/`quantity` from the permanent snapshot (`buildFT1` already supported all of these — this rewire is what actually sources them). - **`BillingDictionarySection.tsx`** (`components/Config/System/`) — **New**, real admin UI for the per-billingCode model: one row per billingCode (its current ACTIVE version) in the main table, full append-only version history behind "History," "New Version" with the real governance rules enforced in the form itself. **Real, important finding along the way**: `ProductivityTab.tsx`/`ContributionDashboardPage.tsx` genuinely, still depend on the *old* whole-table `mockRvuCodeMapService` for physician productivity dashboards — a real, separate, still-needed use case. `RvuCodeMapSection.tsx` was **not** removed or replaced — both screens coexist, relabeled for clarity ("Billing Dictionary (Charge Capture)" vs. "RVU Code Map (Productivity)").

## A real, deep TypeScript issue found and worked around here

While building this, a persistent type error surfaced that looked like a narrowing bug in application code. Isolated it down to a minimal, from-scratch reproduction with zero connection to this folder's files, and traced it to a genuine, project-wide `tsconfig.json` setting (`strictNullChecks: false`): with it disabled, implicit truthy narrowing on a discriminated union's boolean discriminant (`if (res.ok) {...} else {...}`) is unreliable in this project's TypeScript configuration. Deliberately did NOT change that global setting — it could surface unrelated errors across the whole codebase. The real, verified, local fix is explicit `=== false`/`=== true` comparisons instead of implicit truthy checks, used in `RvuCodeMapSection.tsx`. **Worth knowing if this pattern resurfaces elsewhere in this codebase** — it's a real, general limitation of this project's TypeScript config, not specific to this folder.

## Is this "demo" data, and does it get swapped for the real thing in production?

Neither framing is quite right, and it's worth being precise:

- **It's not demo/fake data.** The five values in `CODE_MAP_TABLE` are real, verified 2026 CMS work RVU figures. The honest limitation was always scope (five codes, not ~10,000+), not authenticity.
- **There's no automatic "swap."** Getting the full CPT code set isn't an engineering task — it requires a real, commercial AMA license, since CPT is their copyrighted intellectual property. That's a business/legal decision, not something resolved in code.
- **But most of a real, full dataset doesn't need that license at all.** The actual CMS PPRRVU file — the one with every code's real work RVU value — is itself public, CMS-derived data, verified via direct search (see `parseRvuUploadRows()` above). The part that's genuinely AMA-copyrighted is the official, full-text code *descriptions*, not the RVU values. A real, unlicensed CMS PPRRVU download can be uploaded through the admin UI today.
- **The versioning architecture already scales to this.** Whether it's today's public CMS file or a future, fully-licensed AMA dataset, the path is the same: get the data into a spreadsheet, upload it through Config → System → RVU Code Map, set a real effective date, activate it. No code change needed at that point — that's what this was built for.

## Per-stain-type code resolution (per direct guidance on antibody/multiplex nuances)

Per direct correction: not every IHC stain follows the generic first/additional rule — a specific antibody can be billed differently, and a real multiplex panel (e.g. "PIN-4") is billed as a single 88344, not counted as separate stains:

- **`StainType.defaultCptCode`** (`services/stains/`) — real, optional, coder-configured code for a *specific* stain type record. Each antibody (and each real multiplex panel) is already its own distinct `StainType` record in this dictionary, so this gives real, per-record granularity rather than a blunt, one-size-fits-all rule.
- **Real precedence in `suggestBlockAncillaryCptCodes`**: a stain's own configured `defaultCptCode` always wins first; only stains without one fall through to the generic Special Stain (88312) / first-IHC-88342/additional-IHC-88341 rule. A configured stain still counts toward the generic rule's running IHC count for any later, unconfigured stain on the same block.
- **`resolveStainType()`** (`services/stains/stainCategoryLookup.ts`) — the real lookup this resolution needed already existed in spirit as `resolveStainCategory()`; extracted the full record lookup as its own function, with `resolveStainCategory()` now a thin wrapper on it, rather than duplicating the same name-matching logic.

## Real, critical bug found and fixed: IHC counting is per SPECIMEN, not per block

Per direct, authoritative guidance (AMA CPT Codebook, cross-referenced against eviCore/Premera/APS Medical Billing clinical policy references): qualitative IHC/immunocytochemistry codes (88342 initial, +88341 each additional) are assigned **per unique specimen**, not per slide or paraffin block. The original implementation reset its IHC count at every block boundary — a specimen with IHC stains split across two blocks would have wrongly issued a second "initial" 88342 instead of the real, correct 88341.

- **`suggestSpecimenAncillaryCptCodes()`** — the real fix. Threads one running IHC count across every block on a specimen, in real block order, rather than each block starting its own count at zero. `suggestBlockAncillaryCptCodes()` is preserved unchanged for callers that genuinely only have one block's context (existing tests exercising the rule in isolation); both share the same core logic (`suggestAncillaryCodesForStains`), not duplicated.
- **Real consumers fixed**: `computeCaseCodingSummary()` (was independently calling the per-block suggester for each block) and `BlockStainEditorModal.tsx`'s live suggestion UI (now computes suggestions once per specimen, grouped by real specimen id, and gives each block its own real slice — rather than each block's `BlockCptSuggestion` component computing its own suggestions in isolation).
- **`dftBuilder.ts` was never affected** — it only ever emits real, already-applied codes (`block.coding.cpt`), never calls the suggestion engine at all, per its own established, deliberate scope (never sends the honest estimate as a real charge).

## Additional real codes confirmed, per the same authoritative guidance

- **88344 (multiplex)** and **88360/88361 (quantitative/semi-quantitative morphometric analysis, manual vs. computer-assisted)** are real, distinct codes beyond the basic 88342/88341 pair. All three are usable today via the existing `StainType.defaultCptCode` per-stain override mechanism (`services/stains/`) — no new code was needed, since that precedence architecture already handles "this specific stain type gets a different real code than the generic rule."
- **Honest gap, unchanged**: work RVU values for 88341, 88344, 88360, and 88361 remain unverified in `CODE_MAP_TABLE` — same category as 88341's original gap. A real, coder-configured `defaultCptCode` set to any of these will resolve and apply correctly; the RVU contribution is honestly $0 until a real, verified value is added through the admin UI.

## Real, important scope limits — read before extending this

- **This is not a billing system.** No claims are generated, no payer/modifier rules are applied, no GPCI/locality adjustment is modeled. This is workload/productivity tracking only, matching this project's own earlier `WORKLOAD_AND_CHARGE_CAPTURE_SCOPE.md` reasoning (Thread 1: RVU without billing).
- **`CODE_MAP_TABLE`/each version is deliberately a small, curated subset**, not the full CMS CPT file. Extending it needs the same rigor used to build it — real, verified values via direct search against current CMS data, never estimated or guessed.
- **`ruleBasedDefaultCptCodes()` is not physician-entered or physician-confirmed coding.** Must never be presented as billing-ready anywhere in this app. Real manual CPT selection/override UI is a genuine, separate product/UX decision that hasn't been made — this codebase deliberately doesn't invent one unilaterally. Whoever builds that UI should write into the already-real `Case.coding.cpt` field this fallback also reads from.
- **Versions are immutable once created.** To "fix a typo" or apply a new CMS update, create a new version — never edit an existing one's entries. This is what makes historical resolution trustworthy at all.

## Real, single-entry add/edit/duplicate for the RVU Code Map (per direct question, Aug 2026)

Direct question: "is there a reason we do not have a way to add a RVU code outside of using CSV files. Also, can't edit or duplicate?" Confirmed directly — no real architectural reason. `mockRvuCodeMapService.createVersion()` already accepted any real `entries` array; `RvuCodeMapSection.tsx` simply never exposed a path to build that array from a single change, only the bulk-CSV one.

**Real bug found and fixed before it could bite anyone**: `createVersion`'s own validation required *every* entry in a new version to have a positive `workRvu`, with no exception for a genuinely blank one. The real, current active seed version already contains four honestly-unverified codes (IHC-ADDL/PIN4-PANEL/FROZEN-FIRST/FROZEN-ADDL — see the Charge Capture section above). Building single-entry add naively would have meant every real save silently failing, rejected by pre-existing gaps unrelated to what was actually being changed. Fixed: only rejects a `workRvu` that's present but invalid (`e.workRvu !== undefined && !(e.workRvu > 0)`), matching the same "blank if unverified" principle already established elsewhere in this folder. Confirmed the real CSV upload path (`parseRvuUploadRows`) was unaffected — it already filters invalid-`workRvu` rows out before they ever reach `createVersion`.

`RvuCodeMapSection.tsx` gained a real `EntryModal` (add/edit/duplicate all route through it, reusing the exact `ps-ms-overlay`/`ps-ms-modal` pattern already proven in `BillingDictionarySection.tsx`), a real "+ Add Code" button, and real per-row "Edit"/"Duplicate" actions in the active-version table. All three compute a real, new entries array from the current active version's own entries and call the same `createVersion` + `activateVersion` pair the upload flow already uses — no second, parallel write path. The active-version table also now shows an honest "Unverified" label (matching Billing Dictionary's own convention) for any entry with no `workRvu`, rather than a bare blank.

## Known, disclosed gap: MatrixBlock (Biopsy Array) cases have zero billing coverage today

Found via direct user feedback on `BillingReviewPanel.tsx` ("how will this work in Biopsy Array?"), then traced through the real code before being written up here — not theoretical.

`computeCaseCodingSummary()` (this folder's own real entry point for the whole AI Billing Code Review system) takes only `specimens` and walks each one's own `blocks[]`. A Biopsy Array (`types/case/MatrixBlock.ts`, `useSpecimenBlockManagement.ts`'s `handleCreateBiopsyArray`) is a genuinely different real structure — multiple specimens' tissue sharing one physical cassette, represented as a single `MatrixBlock` living in its own case-level `caseData.matrixBlocks[]` array, with each participating specimen only holding a reference (`Specimen.matrixBlockIds`), not an owned block record. The stains that would drive ancillary billing suggestions (IHC-FIRST, special stains, etc.) live on the `MatrixBlock`'s own `slides[]`, which this function never looks at.

**Real, concrete impact**: for any specimen participating in a Biopsy Array, `computeCaseCodingSummary()` — and therefore `BillingReviewPanel.tsx` entirely — silently shows nothing. No pending suggestions, no applied codes, no indication anything is missing. Not a display bug in the panel; the underlying data this whole system is built on genuinely never reaches a `MatrixBlock`.

**Deliberately not fixed yet** — this isn't a small patch. A real fix needs an actual billing-expert decision on how ancillary stains on one shared, multi-specimen block should attribute for billing purposes (one code per specimen? one shared code? something else CMS-specific?), not just a mechanical "also read `matrixBlocks`" change. Tracked as a real Jira bug once that guidance comes back — see that ticket for the concrete next steps once scoped.
