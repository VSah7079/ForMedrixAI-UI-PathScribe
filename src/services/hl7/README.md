# services/hl7/

Standard-conformant HL7 v2.5.1 ORM^O01 message builder, with a vendor-adapter seam for receiving-system-specific quirks. **Phase 3 addition**: a real DFT^P03 (financial transaction) builder — the outbound side of the specimen/block-level CPT association work in `types/case/Specimen.ts` and `services/billing/`. **Phase 1 addition (Patient/Encounter subsystem): the first real INBOUND direction** — everything above this is outbound (PathScribe data → HL7 text); `hl7Parser.ts`/`adtParser.ts`/`processAdtMessage.ts` go the other way (real HL7 text received from an external system → structured data, wired into the real MPI and Encounter services). **Real fix, Phase 2 of the facility-timezone effort**: every real HL7 TS (Timestamp) field this folder produces now carries the real, signed FACILITY UTC offset (e.g. `-0700` for Tucson), not the sending browser/device's own offset — per direct HL7 v2.x guidance (a TS field's offset must reflect the real, originating facility; sending a browser-local offset breaks message parsing at the receiving LIS). See `utils/facilityTime.ts`. **New addition — a second, deliberately different inbound shape**: `processBlockExceptionEvent.ts` ingests PathScribe's own canonical event contract (`types/events/BlockExceptionEventPayload.ts`) directly, rather than parsing raw HL7 text like everything else in this folder — see that file's own writeup below for the real reasoning (no field-verified Cerebro/Vantage integration guide exists yet, so PathScribe ingests its own, fully-owned specification and leaves the vendor-format translation to a real interface engine, once one exists).

**Pattern:** DELIBERATE PRE-INTEGRATION SCAFFOLDING for the outbound builders — nothing in the app currently calls either. The inbound parsing pipeline is genuinely, actively wired into real services (`services/patients/`, `services/encounters/`), even though nothing in the app yet calls `processAdtMessage()` from a real transport layer (no inbound HL7 listener exists yet — that's real, separate infrastructure work, not a gap in this folder).

Rather than block real, working PathScribe-side ingestion logic on a vendor spec that doesn't exist yet, this file's own specification is the thing PathScribe fully owns and controls — buildable, testable, and real today.   Idempotent on `messageId` (a redelivered event is a no-op, not a duplicate write — same real discipline as every sequence-controlled `update*()` method above), looks up the real case by `internalCaseId` first, falling back to `accessionNumber` (the two resolve to the same real lookup in this app's current data model, kept as two separate fields for the same forward-compatibility reason `ModeAOrderPayload` already does), and every outcome (`applied`/`already-applied`/`case-not-found`/`block-not-found`/`invalid-payload`) is a distinct, honest result. ## Real, extracted pure mutation logic — a second, real backend ingestion path (Aug 2026)

`processBlockExceptionEvent.ts`/`processMaterialLocationEvent.ts` above describe the frontend's own real ingestion — but a real, external Cassette Engine can't call a frontend function directly, and this app's now-confirmed hosting platform (Vercel serverless functions, `api/webhooks/engine/` — see that folder's own README) needed the exact same real business rule reachable from a backend context too. Rather than duplicate the logic a second time (real, avoidable risk of the two silently drifting apart), the actual per-event mutation rule was extracted into two new, pure files with zero dependency on `caseRouter` or any other IO:

- **`blockExceptionMutation.ts`** — `applyBlockException()`, the exact real block-status-and-exception-fields update `processBlockExceptionEvent.ts` used to compute inline, now pure: given a case's current `specimens` array and the event's own fields, returns the new, full specimens array (or `null` if no matching block exists) — nothing else.
- **`materialLocationMutation.ts`** — `applyMaterialLocation()`, same real extraction for all 8 real target levels (specimen/block/slide/aliquot/decant/decant_slide/decant_aliquot, plus the two case-level matrix_block/matrix_slide levels). **Real bug caught during extraction, before it shipped**: an early draft used the wrong field name (`stains`) for a matrix block's own slides array — the real field, confirmed by diffing directly against the untouched original file rather than trusting memory of an earlier, truncated read, is `slides`. Fixed and locked in by a real, dedicated test before the mistake ever reached the extracted file's real consumers.

`processBlockExceptionEvent.ts`/`processMaterialLocationEvent.ts` themselves were refactored to call these pure functions and do nothing else differently — the Dev Tools "Sim" buttons' own behavior is unchanged, byte-for-byte, confirmed by diffing every real branch against the pre-extraction original. The real, new consumer is `api/webhooks/engine/block-exception.ts`/`material-location.ts` — genuine Engine-facing endpoints that call the exact same pure functions, then write via `applyEngineCaseUpdate` (Admin SDK, transactional) instead of `caseRouter.updateCase()` (client SDK). A real Engine-reported exception and a Dev-Tools-simulated one now apply the identical business rule, through two different, real write paths — not two independent, potentially-diverging ones.

Two further, real, notification-only siblings exist alongside the mutating functions above, and are **not** interchangeable with them:

- **`notifyBlockExceptionApplied.ts`** / **`notifyMaterialLocationApplied.ts`** — real, deliberately separate functions that only show a toast; neither touches case data at all. Needed because the real backend webhook has already applied the mutation server-side by the time a notification record exists for a poll to find (`src/hooks/usePendingEngineNotifications.ts` — see that folder's own README) — calling the *mutating* `processBlockExceptionEvent`/`processMaterialLocationEvent` from that poll loop would silently apply the same real change a second time. The mutating functions stay reserved for the Dev Tools Sim buttons' own no-backend-involved flow; the notify-only functions are what the real, Engine-driven path actually uses.
