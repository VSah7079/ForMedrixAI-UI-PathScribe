## Real, per direct guidance ("do we implement ORU^R01 dispatch trigger then actual outbound HTTP dispatch transport" → "we can setup just the receiving end for now" → "Dispatch needs to be generic so all transactions can be checked"): the real outbound HTTP dispatch transport this whole app has never had

Real, per direct follow-up on the architectural boundary documented throughout this app ("nothing dispatches this yet, no real HTTP transport exists") — genuinely, partially closed for the first time. Two real, separate pieces:

**The real receiving end**: `receive_interface_message`, a new Firebase Cloud Function alongside `render_report` in the same `functions/main.py` (a separate repository from this frontend — see that file's own header comment for the exact contract). Deliberately never generates HL7 itself — a real stand-in for an interface engine's receiving side (Mirth Connect/NextGen Connect or similar), built specifically to verify PathScribe's own outbound JSON is correct, never a Mirth Connect replacement. Accepts one real, generic envelope shape (`queueEntryId`/`transactionType`/`dispatchedAt`/`payload`) used by every real transaction type, rather than four independently-shaped request bodies — validation deliberately stops at that envelope level rather than deep-validating each of the four real payload shapes field-by-field, since those are already defined and enforced by TypeScript on the sending side. **The real dispatch side**: `services/interfaceDispatch/dispatchInterfaceMessage.ts` — one, single, real, generic dispatch function every real outbound queue calls, rather than one dispatch implementation per transaction type. Wired into `pages/OutboundInterfaceDlqSection.tsx`'s own real "Dispatch Now"/"Retry Dispatch" actions for the patient-ADT and ORU^R01 queues — builds the real payload via the existing real builder functions (`buildAdt08Payload`/`buildAdt40Payload`/`buildAdt47Payload`/`buildOruR01Payload`), POSTs it, and only transitions a queue entry to a genuinely-earned `SENT` on real success, or `FAILED` with the real, actual error otherwise. Simulate Failure stays exactly what it always was — a real, honest testing aid, never confused with a real dispatch attempt.

**Real, honest scope boundary specific to the LIS-sync queue, worked through directly rather than assumed**: its own real payload (`embeddedHeader`/`fullPayloadText`) is built from a real, ephemeral parameter (`payloadBody`) that's never persisted anywhere — unlike the other three transaction types, it genuinely can't be rebuilt later from just the queue entry's own reference fields. `OutboundInterfaceDlqSection.tsx`'s own `buildPayload` is deliberately `null` for this queue type, with a clear, honest UI message rather than silently sending an incomplete payload. Real dispatch for this type instead happens immediately, fire-and-forget, at the one real moment the full payload actually exists — `pages/SynopticReportPage/hooks/useLisIntegration.ts`'s own `sendSynopticReportToLis`, right after the payload is built and the lightweight queue reference is enqueued. Deliberately fire-and-forget, not gating the real sign-out/amendment-release flow it's attached to — a real, external network call must never block a real, time-sensitive clinical action, same real reasoning as the enqueue itself already had.

**A real, found-and-fixed TypeScript gotcha worth remembering for any future work in this codebase**: `dispatchInterfaceMessage`'s own result type was first written as a discriminated union (`{ok: true} | {ok: false, error: string}`), which produced a confusing, hard-to-reproduce compile error (`if (result.ok) {...} else {...}` narrowed the `else` branch to `{ok: true}`, the wrong branch) that isolated repro files couldn't reproduce under `--strict`. Root cause: this project's own `tsconfig.json` has `strictNullChecks: false`, under which TypeScript's control-flow narrowing on a boolean-literal discriminant doesn't reliably work the way it does under strict mode. Fixed by not relying on discrimination at all — `error` is simply optional on both branches (`{ok: boolean; error?: string}`) instead.

**A real, related, fifth outbound transaction type — flagged here as out-of-scope, then addressed as a real, direct follow-up (see `services/interfaceEngine/README.md`'s own account)**: `services/interfaceEngine/`'s own `OrderCreated` (Category E) event, whose own header comment explicitly anticipated this exact moment ("When the real backend exists, only this file's own real implementation swaps"). It now genuinely dispatches, via the same real, generic `dispatchInterfaceMessage()`/`receive_interface_message` every other real transaction type uses — `ORDER_CREATED` added to `InterfaceTransactionType` and the backend's own `_VALID_TRANSACTION_TYPES` — with `delivered` finally meaning what its own original doc comment always said it eventually should.

## Real, per direct follow-up ("We are logging interface errors with human readable error messaging?" → "continue with the error log refinements"): a direct question, answered honestly rather than assumed — the real answer was "partially," and three real, concrete gaps got fixed

Traced the whole real dispatch pipeline end to end before answering rather than guessing — found three genuine, separate problems, all now fixed:

**1. `errorCode` was too coarse to mean anything for a real failure.** Every real dispatch failure (never the Simulate Failure testing buttons) hardcoded `errorCode: 'DISPATCH_REJECTED'` at every real call site, regardless of whether the real cause was a network failure, a timeout, or a genuine rejection — `'DISPATCH_TIMEOUT'` could never actually be produced by a real failure at all. Fixed with a new, real, meaningful third code: `'DISPATCH_UNREACHABLE'` — the real network call itself failed (connection refused, DNS failure, CORS), the receiving endpoint never got the request at all, distinct from `'DISPATCH_REJECTED'`, where the request genuinely reached the receiver, which responded with a real, non-2xx status. These mean genuinely different things operationally (the engine may be down vs. the engine is up but rejected this specific message) and previously both collapsed into the same code. `dispatchInterfaceMessage()` now resolves the real code itself, once, at the one real place a dispatch actually happens — every real caller (`OutboundInterfaceDlqSection.tsx`, `useLisIntegration.ts`) reads it off the result instead of independently guessing/hardcoding one.

**A real, related fix that made `'DISPATCH_TIMEOUT'` achievable for a real failure at all**: a bare `fetch()` with no timeout mechanism hangs indefinitely on a genuinely unresponsive endpoint. Added a real, explicit 15-second timeout via `AbortController` (matching the same real value `simulateInterfaceDispatchFailure.ts`'s own simulated timeout message already referenced, for consistency) — an `AbortError` from this real, own-initiated abort is now the one real path that produces `'DISPATCH_TIMEOUT'`, distinguished from other real network failures by checking `e.name === 'AbortError'`.

**2. The freeform error message quality varied a lot by failure type, and two real paths were genuinely unhelpful.** A non-2xx response with no parseable JSON body fell back to a bare `HTTP 500` — no explanation at all. A real network-level failure surfaced only the raw browser/JS exception string (`"Failed to fetch"` in Chrome) with no context. Fixed by wrapping every real failure path in a real, plain-language frame while keeping the real, technical detail alongside it, never replacing it: `"The interface engine rejected this message: [detail]"` / `"The interface engine returned an unexpected error (HTTP 500)."` / `"Could not reach the interface engine — check that it's running and reachable at the configured endpoint. ([technical detail])"` / `"The interface engine did not respond within 15 seconds — it may be down, overloaded, or unreachable."`

**3. The audit trail dropped the real, detailed message entirely, and a failure that was never retried left zero permanent record at all.** Checked directly: every real `retryDispatch()` across all three queue services logged only the coarse `errorCode` to the audit log (`` `...was: ${prior.errorCode}` ``), never `errorMessage` — the actual, meaningful detail never made it into the permanent record even when a retry did happen. A more significant real gap found in the same pass: `markFailed()` itself logged nothing at all — only a *later* `retryDispatch()` created any audit record, referencing the *prior* failure. A real dispatch failure that was never retried (left sitting in the DLQ, or superseded by an unrelated later success) had no permanent audit trail whatsoever — only the live queue entry's own `errorCode`/`errorMessage`, silently overwritten by the next attempt. Fixed both: every real `retryDispatch()` now includes the real `errorMessage` alongside the code, and `markFailed()` itself, in all three queue services, now logs a real, permanent audit event the moment a real failure actually happens, independent of whether it's ever retried.

**Real, direct verification, not just written and assumed**: a new, dedicated test file (`dispatchInterfaceMessage.test.ts`, 7 tests) covers the real success path and all three real failure modes — including the real timeout mechanism, verified with real fake-timer control (`vi.advanceTimersByTimeAsync`) against a `fetch()` mock that genuinely respects the passed `AbortSignal`, rather than either waiting 15 real seconds or only asserting the timer fired in isolation. A new test in each of the three queue services' own real test files (`outboundPatientAdt.test.ts`, `mockReportVersionService.test.ts`, `useLisIntegration.test.ts`) independently confirms `markFailed()`'s new audit-logging fix works correctly in each — not assumed correct from the same copy-paste pattern alone.
