# services/import/

New folder. Real, decoupled document-import engines — content extracted here has no coupling to any specific PathScribe data model. A thin adapter elsewhere maps the generic output into whatever real record type actually needs it.

**Pattern:** Standard interface/mock/firestore pattern doesn't apply here — there's no CRUD, no persistence. Each engine is a pure(ish) async function: take a real file, return a generic, structured list of what it found.

## Files

- **`wordBuildingBlocksEngine.ts`** (+ `.test.ts`, `__fixtures__/test-buildingblocks.dotx`) — **New**, per direct guidance ("a mechanism to take MS Word AutoText / Building Blocks and load them into personal macros — or could that be an engine function?"). Confirmed the real answer is yes: this knows nothing about `Macro`/`VoiceMacro`/PathScribe's own data model at all. It unzips a real `.dotx`/`.dotm`/`.docx` (via `jszip` — a real, new dependency; confirmed directly this project had zero ZIP/XML parsing capability before this) and parses the real OOXML "glossary document" part (`word/glossary/document.xml`) that Word actually stores every AutoText/Building Blocks entry in, returning a generic `ExtractedBuildingBlock[]` (`name`/`gallery`/`category`/`content`). `components/Config/Macros/MacroPanel.tsx`'s own "Import from Word" button is the one real, current consumer — a thin adapter that maps this generic output into real `Macro` records (see that folder's own README entry). Real, deliberate scope boundary: extracts plain text only, not full rich-text/formatting — a real, much larger undertaking (see this file's own header for why).

  **A real, valuable bug caught by testing against an actual fixture, not a hypothetical:** `happy-dom` — this project's own real test environment — silently falls back to HTML parsing for `DOMParser`'s `'application/xml'` mode. Two real consequences confirmed directly: it mishandles self-closing custom elements (`<w:name .../>` gets treated as an *opening* tag, corrupting the whole subtree), and it never splits a namespace-prefixed tag name — `w:docPart` comes back as one literal local name, not prefix + local name the way a real, standards-compliant browser reports it. Fixed by matching element names case-insensitively AND against both the bare and fully-prefixed forms — a genuine robustness improvement for any lenient/nonstandard parser an admin's own untrusted uploaded file might have been generated by, not just a workaround for this one test environment.

  Real test fixture (`__fixtures__/test-buildingblocks.dotx`) built with Python's own real `zipfile` module against the actual OOXML schema — not a mock. Uses non-self-closing tags for empty elements specifically to work around the happy-dom limitation above; a real Word-generated file would normally self-close them, and the extraction logic (case-insensitive, dual-form matching) handles both forms correctly regardless of which one a given file uses.
