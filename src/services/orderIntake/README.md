# services/orderIntake/

The pending-orders queue an accessioner pulls from, and the resolution chain turning a raw external order into real Client/Department references.

**Pattern:** Standard interface/mock pattern (no firestore stub currently).

## Notes

- Multi-step design: raw IncomingOrder never written directly into Case; Facility resolution reuses Facility.assigningAuthority as the crosswalk key; Specimen resolution needs its own crosswalk since the same external code means different things at different facilities.
- **Real admin UI, closing a gap flagged directly.** `listCrosswalkEntries`/`addCrosswalkEntry` were real and already implemented, with zero UI anywhere — confirmed directly. Now has one: `components/Config/Integrations/CrosswalkSection.tsx`, in the new Integrations config tab. Shows both admin-entered mappings and the real, system-learned "pending" entries `resolveOrder()` already creates on an unrecognized code, distinguished by `createdBy`. **CSV/spreadsheet import added** (same two-step preview-then-apply shape as Stain/Specimen Dictionary) — Facility and specimen type matched by *name*, not id, since a real customer's spreadsheet has no way to know PathScribe's internal ids; an unresolvable name surfaces as a visible per-row error rather than being silently skipped or guessed at. Matching an existing `[clientId, externalCode]` pair now updates rather than erroring/duplicating, which needed a new `updateCrosswalkEntry()` method — the interface previously only had `add`.
- **Order-type-mapping work, Step 1 of a multi-step build (types only, no behavior change yet):** cross-checked an external "Order Type Mapping" spec against this codebase before building anything — confirmed real overlap with what's already here (`SpecimenCodeCrosswalkEntry` already resolves to a `SpecimenEntry` that carries both category AND subspecialty, so no new "Order Type Dictionary" entity is needed) rather than building a parallel system. `SpecimenCodeCrosswalkEntry` gained two optional fields: `codingSystem` (`'HL7_LOCAL' | 'LOINC' | 'SNOMED'` — a real crosswalk entry can now be scoped to a specific coding system, not just a bare code string) and `siteId` (optional per-`Organisation`-`Site` scoping, for a multi-site organisation that wants the same client's code to route differently per site — absent means org-wide, same convention as `Facility.performingLabFacilityId`'s own undefined-means-global pattern). `IncomingOrderSpecimen` gained `externalCodingSystem` to match, populated by the interface engine (PathScribe doesn't parse raw HL7 itself — see `services/hl7/README.md`'s own architecture note). New `utils/normalizeOrderCode.ts` provides the real normalization pass multi-coding-system priority matching will need. Next real step: wire multi-code priority matching (local → LOINC → SNOMED → description fallback) into `resolveOrder()`, and raise a real `InterfaceException` (`eventType: 'unmapped_order_code'` — see `services/interfaceExceptions/README.md`) alongside the existing auto-create-and-continue fallback, not instead of it.
