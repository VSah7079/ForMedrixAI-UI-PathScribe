# types/quality/

The generic types PS-108's real QA Activity Framework builds on.

## Files

- **`QaActivityType.ts`** — **New (PS-113).** The real, admin-configurable definition of a "review-with-outcome" QA activity — the first of two real archetypes. Checked directly against the old `ReconciliationRecord`'s own real fields before this was written, not designed in the abstract — confirmed `frozenCategory`/`finalCategory`/`frozenDx`/`finalDx` are genuinely activity-specific comparison fields, not generic to the archetype, so they live in this type's own `fields[]` schema (mirroring `EditorField`/`EditorTemplate`, `components/Config/Protocols/SynopticEditor.tsx`'s real, proven field-type-driven pattern — same real field-type set, dropdown/radio/checkboxes/numeric/text/longtext), never as fixed properties on the generic record. **Real fix (PS-115):** `jurisdictions` was typed as bare `string[]` — fixed to the real `Jurisdiction` enum, which caught a genuine, already-shipped bug: the seed data carried `'EU'`/`'UK'`, neither a real jurisdiction value in this app, meaning a UK site would never have seen a CAP/ISO-15189-mandated Standard activity in its own tab at all. Also gained `samplingPercentage` (Story 1.2, mirrors `shouldRandomlySampleForCodeReview.ts`'s own real percentage convention) and `capaTriggerRule` (Story 1.4, wired to the real, existing Deficiency/CAPA foundation — `services/deficiencies/`, not a new system).
- **`QaActivityRecord.ts`** — **New (PS-113).** The generic review-with-outcome instance record — the direct generalization of the old `ReconciliationRecord`, field-by-field. `outcome` and every discrepancy-detail field (delta/severity/rootCause/comments) stay real, structural, top-level properties — genuinely generic to the whole archetype, confirmed directly (the same discrepancy-classification concepts apply equally to a future Cytology-Histology correlation or IHC QC discordance). Real, deliberate rename, per direct guidance ("Teaching-Onboarding," not just "Teaching," to read as versatile rather than academic-medicine-specific): `isTeachingCase` → `isTeachingOnboardingCase`, `attendingFeedback` → `reviewerFeedback` (kept consistent with this same record's own `recordedBy`, rather than introducing a third term for the same real role). `draftedBy` carried forward unchanged — already neutral. **Real, current status (PS-113, Stage 5): the sole type for this data.** `ReconciliationRecord.ts` — the old, real type Discordance originally ran on — is retired and deleted (first release, no real production history to preserve). Every real consumer, and the modal that creates these records, now uses this type exclusively.
- **`QaSupervisionAssignmentType.ts`** — **New (PS-114).** The real, admin-configurable definition of a "supervision/assignment" QA activity — the second real archetype, deliberately separate from `QaActivityType.ts` above. Checked directly against the old `FppeAssignment`'s own real, complete shape before this was written: provider-scoped rather than case-scoped, an ongoing period rather than a discrete event, no discrepancy-detail concept at all. Carries no `fields[]` schema, unlike `QaActivityType.ts` — there's no equivalent "reviewer fills in an answer" concern here; a supervision assignment's own real configuration is its end condition and scope. **Real fixes (PS-115):** same `jurisdictions` → `Jurisdiction[]` fix as `QaActivityType.ts` above; also gained `duplicatedFromId` — a genuine gap found while scoping the Configuration Center, since `QaActivityType.ts` already had this field from PS-113 but this type never did, which would have made Duplicate provenance tracking asymmetric across the two archetypes.
- **`QaSupervisionAssignment.ts`** — **New (PS-114).** The generic supervision/assignment instance record — the direct generalization of the old `FppeAssignment`, field-by-field. Real, structural difference from `QaActivityRecord.ts`: **not** an append-only, "always written, never edited" record — a real assignment gets mutated in place over its own lifetime (`casesReviewedCount` incremented, `status` transitioned to `'completed'`), matching `FppeAssignment`'s own real service methods, not a new design invented here. Real, deliberate naming generalization, same discipline as Teaching-Onboarding: `provisionalUserId`/`proctorUserId` (genuinely FPPE-specific terms) became `superviseeUserId`/`supervisorUserId`, reusable for a future, different supervision-style activity.
