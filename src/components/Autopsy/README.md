# components/Autopsy/

UI for the Autopsy Pathology Module (PS-261). Real, presentational components only — all business logic lives in `services/autopsy/`, which this folder only calls and renders.

**Standing conventions applied in `AutopsyAuthorizationCompletionForm.tsx`, per direct instruction:** no inline CSS (real classNames from `pathscribe.css`'s existing design system only — `ps-conf-*` shared classes plus a small set of new `ps-autopsy-*` classes for anything genuinely new), no inline logic (validation/transform/status functions all live in `services/autopsy/`), no text strings (every piece of UI text goes through `useTranslation()`, translated across all 5 locales under the `autopsyIntake.*`/`autopsyAuthCompletion.*` namespaces). See "Retired" below for where this folder's Autopsy work in `AccessionPage.tsx` deliberately does NOT follow this.

## Files

- **`AutopsyAuthorizationCompletionForm.tsx`** — the completion form for the legal hard-stop gate itself. Takes a case's existing `AutopsyCaseDetails` (built at intake) and lets staff enter the real, previously-missing written order (forensic) or consent grant (hospital-consented), showing what's already on file for context and a live preview of whether submitting would actually unblock gross examination (`resolveAutopsyGrossExaminationGate`) before they do. Still needed as its own screen: this is a genuinely later, separate workflow step (completing paperwork on an already-accessioned case), not something `AccessionPage.tsx` itself would ever handle. **Now genuinely wired (per direct follow-up), and a real, deeper gap this surfaced and closed**: investigation found neither this form nor `resolveAutopsyGrossExaminationGate.ts` had ANY real UI caller anywhere in the app — the completion workflow (gate check, form, persistence) was built and unit-tested but never actually mounted. `SynopticReportPage.tsx` is now that real first caller: a banner shows whenever the gate blocks the case, opening this form in a modal; its own `handleAutopsyAuthCompletionSubmit` persists via `caseRouter.updateCase()` + `knownVersionRef`, the same pattern the file already uses for every other gate-resolution handler (e.g. `handleFixativeGateContinue`).

- **`AutopsyBodyReleaseForm.tsx`'s own mounting gap — now also closed** (per direct follow-up). Same real, previously-unmounted state as the authorization form was, now mounted the same way: a second, separate banner in `SynopticReportPage.tsx` — shown only once `resolveAutopsyBodyReleaseGate` is genuinely allowed AND the body hasn't already been released (a real, separate check, `resolveAutopsyBodyAlreadyReleased.ts`, since the release gate itself only checks current eligibility, never history — see that file's own header comment). This form's own `onReleased` differs from the authorization form's `onSubmit`: it calls `releaseAutopsyBody.ts` directly (fetch, gate re-check, persist all internal) and returns no updated data, so the real mounting re-fetches the case via `caseRouter.getCase()` afterward — the same established refresh pattern this page's own `MATERIAL_SCAN_UPDATED_EVENT` listener already uses — rather than a second, separate local patch that could drift from what was actually persisted.
- **`getMainBodySpecimen.ts`** — per a real, direct follow-up suggestion ("a quick helper... could provide a central place to update that logic system-wide"), the "which specimen is the body" heuristic (first specimen on the case, matching Part B's own Rule Set 4 convention that the main body/trunk is always Specimen "A" even when separately-excised organs are also present) is now this one, real, centralized function rather than inline at each of `SynopticReportPage.tsx`'s own two call sites. There's still no dedicated "this is the body" marker on `Specimen` itself — this is deliberately the one real place to add an explicit-designation check first, ahead of the index-0 fallback, if one is ever added.
- **`AutopsyBodyReleaseForm.tsx`** — item 4's own UI, and deliberately different from the other two forms here: per direct guidance's own "continue with wiring and UI," this component actually calls the real, async `releaseAutopsyBody.ts` itself (fetch, gate re-check, persist) rather than handing built data back to a caller. Shows the gate's own blocked reasons directly when release isn't yet allowed; only shows the release fields once it is.

## Retired

- **`AutopsyIntakeForm.tsx`** — removed (per direct guidance: "should these additional fields become visible when an autopsy specimen has been picked?"). Its own fields now live directly inside `AccessionPage.tsx`'s own `autopsyRelevant`-gated section instead of a separate, standalone screen — the same real, established pattern `cytologyRelevant` already uses there. Its underlying pure logic (`resolveAutopsyIntakeFormValidation.ts`, `buildAutopsyCaseDetailsFromIntakeForm.ts`, both in `services/autopsy/`) is NOT retired — `AccessionPage.tsx` calls both directly, and their own tests still stand.
- Real, honest note: `AccessionPage.tsx`'s own integrated Autopsy section does NOT follow this folder's i18n convention (`useTranslation()`/`autopsyIntake.*`) — it matches that file's own pre-existing, hardcoded-English convention instead (same as `cytologyRelevant`'s own section right next to it), consistent with `AccessionPage.tsx` being part of the app-wide i18n sweep (PS-269) deferred until Autopsy itself is feature-complete, per direct instruction. The already-built `autopsyIntake.*`/`autopsyAuthCompletion.*` i18n content across all 5 locales is unused for now but not deleted — it's exactly what that later sweep would draw on.

## Full wiring pass — "it all needs to be wired" (per direct follow-up)

A direct audit (every pure Autopsy function checked for a real UI consumer via full-codebase search, not assumed from having tests) found six functions with zero real callers anywhere. Each is now genuinely wired:

- **`resolveAutopsyAccessionStatus.ts`** — an always-visible status badge in `SynopticReportPage.tsx` (`ps-autopsy-status-badge--*`, same classes this folder already established). Previously only the gate-blocking banner ever surfaced the 'temporary' state; the positive 'fully_authorized' state had no visible confirmation anywhere.
- **`resolveAutopsyTatSlaMatrix.ts`** — surfaced via a new `formatAutopsyTatSlaSummary.ts` (real range-vs-fixed-figure formatting logic, kept out of JSX) right alongside the status badge.
- **`resolveHtaApplicability.ts`** — gated a field, `AutopsyCaseDetails.organRetentionTier`, that had no UI to set it *at all*. Built a real select plus `handleOrganRetentionTierChange`, shown only for HTA-governed jurisdictions.
- **`resolveConsentingRelativePriority.ts`** — the existing "Relationship" field in `AccessionPage.tsx` is genuine free text; rather than force a schema change, a new `formatConsentingRelativePriorityHint.ts` shows the jurisdiction's own priority order as an informational hint alongside it.
- **`resolveMortuaryStorageOccupancy.ts`** — the deepest gap: the entire Asset Location Dictionary (`services/assetLocation/`) had no admin UI anywhere, meaning no way to even define a real mortuary `storage_slot`. Built `AssetLocationDictionarySection.tsx` (registered in Config \u2192 System, "Lab Materials & Workflows"), exported the service from `services/index.ts` (it wasn't exported at all), and seeded two real `storage_slot` entries. Its own "Mortuary Storage Occupancy" tab queries every Autopsy case's specimens across the whole app (not just the open case) and resolves real-time occupancy.
- **`calculateAutopsyBodyMassIndex.ts`** — wired into `RightSynopticPanel.tsx`'s own central `setAnswer()`: BMI now auto-recomputes on every real weight/height change (including clearing itself if either becomes invalid), and the BMI input is now disabled, matching the spec's own "[Auto-Calculated]" label. Scoped safely by field id — `setAnswer` is shared across every real template, but no other template happens to use these exact field ids.

Two further, real configuration gaps closed in the same pass:
- **Cassette routing** — `proto-autopsy-cardiac-sectioning` had no cassette-color rule at all; added `route-autopsy-cardiac-protocol` (white — the one neutral color not already claimed by an urgency/type convention), confirmed end-to-end in `generateDefaultMaterial.test.ts`.
- **Config discoverability** — neither the Protocol Dictionary nor the new Asset Location Dictionary had any entry in `constants/configSearchIndex.ts`, so searching "autopsy" or "mortuary" in Config found nothing even though the real configuration existed. Added entries for both, plus an "autopsy" synonym on the existing Specimens entry. A genuinely separate, dedicated "Autopsy Config" screen was considered and deliberately not built: the remaining Autopsy functions (TAT/SLA, HTA applicability, consent priority) are hardcoded, spec-derived lookups with nothing for an admin to actually configure — they're fixed logic, not settings, and are already surfaced read-only on the case itself.
